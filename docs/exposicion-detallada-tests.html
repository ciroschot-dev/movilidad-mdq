Análisis Detallado de la Suite de Pruebas

Este documento detalla la lógica interna de los tests que garantizan la estabilidad de MovilidadMDQ.

🛡️ Estrategia de Aislamiento

Para asegurar que los tests sean estables y no dependan de factores externos, implementamos la siguiente configuración:

@SpringBootTest(properties = { "spring.datasource.url=jdbc:h2:mem:testdb", "spring.config.import=" })

Esto garantiza que NUNCA se toque la base de datos de producción (AWS RDS) durante los tests, y que no se necesiten las variables de entorno locales (.env) para validar el código.

1. Capa de Servicios (Business Logic)

ViajeServiceTest

Unitario

Valida el corazón del proyecto: el algoritmo de cálculo de precios.

  • Escenario: testCalcularViajeExitoso
    Mocks: Simula que Google Maps devuelve un viaje de 5km y 10 minutos. Simula que la tarifa del taxi es de $2250 (bajada) y $150 (ficha).
    Validación: Verifica que el precio final del taxi sea correcto según el sistema de fichas de Mar del Plata (Bajada + Fichas por distancia).

UsuarioServiceTest

Unitario

Asegura que la gestión de identidades sea robusta.

  • Escenario: testRegistrarUsuarioExitoso
    Lógica: Valida que al registrar un usuario, la contraseña se encripte correctamente y se genere un Token JWT válido.
  • Escenario: testRegistrarUsuarioDuplicado
    Lógica: Verifica que el sistema lance una excepción RecursoDuplicadoException si alguien intenta usar un username ya existente.

2. Capa de Controladores (API & Seguridad)

ViajeControllerTest

Integración

Valida la exposición de los servicios a través de HTTP.

  • Escenario: testCalcularViajeSinAuth
    Escudo: Intenta llamar al cálculo de viaje sin estar logueado.
    Validación: Debe devolver un error 401 Unauthorized. Esto confirma que Spring Security está protegiendo la API.
  • Escenario: testCalcularViajeConAuth
    Lógica: Simula un usuario logueado con rol USER y verifica que el servidor responda 200 OK.

ViajeHistorialIntegrationTest

Integración Real

Prueba el flujo de datos completo entre el controlador y la base de datos.

Escenario: Guarda un viaje real en la base de datos de prueba y luego llama al endpoint de historial para ver si el viaje "aparece" en la lista del usuario.
Herramienta: Usa H2 Database para no ensuciar la base de datos real de AWS.

3. Capa de Persistencia (Base de Datos)

ViajeRepositoryTest

Data JPA

Valida que las consultas SQL sean correctas.

Escenario: testFindByUsuarioIdOrderByFechaHoraDesc
Validación: Inserta dos viajes y comprueba que al pedirlos, el repositorio los devuelva ordenados por fecha (el más reciente primero).
